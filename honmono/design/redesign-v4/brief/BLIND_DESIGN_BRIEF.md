## 0. この文書の性格

この文書には **WHAT(製品が何であり、何をしなければならないか)だけ**が書いてあります。
**HOW(どう見せるか)は一切書いていません。**

現行UIの見た目(色・書体・間隔・面の丸み・階層・構成要素・配置・装飾)は
**意図的に一切渡していません**。スクリーンショットも現行CSSも同梱していません。
現行の実装に引きずられない状態で、Visual / Interaction / Motion を決めていただくためです。

したがって、この文書に

- 「今はこうなっている」
- 「この構成を踏襲してほしい」
- 「この要素を横に並べてほしい」

といった指定は存在しません。**あるように読めた場合、それは読み違いです。**

Visual Direction・Color Personality・Typography Personality・Composition・Visual Metaphor・
Signature Element・Motion Personality は、**すべてそちらの決定事項**です。

## 1. 製品の事実

**HONMONO(ホンモノ)** — 個人が作っている無料のWebツール群。日本語。

生成AIで「実在しない人物」を無限に作れるようになった結果、
インターネットでは次の3つが同時に起きています。

1. **消費者被害** — なりすまし・ロマンス詐欺・偽アカウントへの課金
2. **クリエイターの埋没** — 実在の活動者がAI量産アカウントに埋もれ、逆に「それAIでしょ」と疑われる
3. **信頼の崩壊** — 見ているものが本物か分からない不信の常態化

HONMONO は「AI美女を作る側」に回らずにこれに対抗します。
**AI生成が増えるほど価値が上がる方向、つまり「実在すること」の証明・検出・可視化**に賭けています。

3本柱:

| 柱 | 意味 |
|---|---|
| 証明する | 実在の人間・実写のコンテンツであることを、来歴データと相互リンクで示す |
| 見分ける | AI製アカウント・なりすまし・詐欺を、誰でも使える道具で検知する |
| 束ねる | 「本物であること」を選んだクリエイターを可視化し、仕事とファンにつなぐ |

## 2. 誰が使うか(優先順)

### ① 疑いを抱えた一般利用者(最多・最優先)

SNSやマッチングアプリで接触してきた相手が実在するか疑っている人。

- **端末はスマートフォンが大半**
- 相手の写真を保存した直後、**その場で**調べたい
- **不安で、急いでいる**
- 「メタデータ」「C2PA」「EXIF」という語を知らない
- 決めたいのは「この相手と関わり続けてよいか」

### ② 実在するクリエイター

イラストレーター・写真家・コスプレイヤー・配信者など。

- PCとスマートフォンの両方
- 「その作品AIでしょ」と疑われ、晴らす手段がない
- 自分のサイトを持てる人と持てない人が混在
- 決めたいのは「どうやって自分の実在を第三者に検証させるか」

### ③ 判定モデルの導入を検討する法人・開発者

- PC
- 画像を自社サーバーに送らずに判定したい。法務審査を通す必要がある
- **数字と弱点とライセンスを見る**。装飾では動かない

### ④ 記者・研究者

- 拡散画像の出所を調べたい。生データまで見る

## 3. この製品の思想(UIが体現しなければならないもの)

### 3-1. 断定しない。それでも行動は決められる。

メタデータは編集・削除できます。したがって

- 「痕跡なし」= 本物、ではない
- 「痕跡あり」= 悪意、でもない

**この限界を隠さないことが製品の中身そのものです。**
限界の説明を小さくしたり、折りたたみに隠したりすることは、機能の削除にあたります。

同時に、**正直さの結果として「で、結局どうすればいいのか分からない」にしてはいけません。**
どの結論にも「次にとれる行動」が併記されている必要があります。

### 3-2. データを外に出さない。

全処理が利用者の端末内で完結します。画像もフォーム入力もチェック内容もサーバーに送りません。
これはこの製品の最大の差別化であり、**現状は文章でしか伝えられていません。**

### 3-3. 数字は実測のみ。都合の悪い数字も出す。

精度は自分で測った値だけを載せています。丸めません。要約しません。
「2025年世代の生成器を約4割見逃す」も同じ大きさで書いてあります。

### 3-4. いちばん避けたい結末

**実在の人を「AI」「偽物」「詐欺」と断定して晒すこと。**

この製品は、実在する人が疑われずに済むために作られています。
結果を外へ持ち出す操作(コピー・画像保存)の直前には、
必ずこの警告が読める必要があります(§7 に厳密な配置制約)。

2番目に避けたいのは、**「判定材料なし」を「本物である」と読ませてしまうこと。**
判定不能は中立であり、**中立に見える必要があります。**

## 4. 画面と、そこで果たされるべきこと

11画面あります。Function Freeze ID は `FUNCTION_FREEZE.json`、状態は `SCREEN_STATE_INVENTORY.json` を参照してください。

| 画面ID | 役割 | この画面で果たされること |
|---|---|---|
| `HOME` | 入口 | このサイトが何者で、自分の用事がここで足りるかが分かる。3つの主要ツールへ送り出す |
| `CHECKER` | 中核タスク | 手元の画像/動画から、AI生成/実写の手がかりを得る |
| `AICHECK` | タスク | 自分の観察を構造化して、アカウントのリスクを評価する |
| `BADGE` | タスク | 自分が実在することを、第三者が検証できる形で公開する準備をする |
| `CREATORS` | タスク | 実在を証明済みのクリエイターを探す/自分が載る方法を知る |
| `REPORT` | 根拠文書 | 判定の実測値・弱点・出典・訂正履歴を確かめる。**このプロジェクトの信頼の根拠** |
| `BUSINESS` | 収益導線 | 判定モデルの導入可否を判断し、問い合わせる。**唯一の収益導線** |
| `DOCS` | 文書 | 目的・使い方・FAQ・制限・プライバシーを読む |
| `LEGAL_PRIVACY` / `LEGAL_TERMS` / `LEGAL_CREDITS` | 法務文書 | 正確に読める |

### 4-1. CHECKER で通らなければならない道筋

```
ファイルを渡す → 待つ → 結論を1つ読む → 根拠を確かめる → 次の手を打つ → 限界を知る
```

- ファイルの渡し方は **選択 / ドラッグ&ドロップ / キーボード** の3つが必要
- 結論は **6種類のうち1つ**(AI痕跡あり / 来歴データ付き / カメラ撮影の痕跡あり / 素材サイト由来 / 弱い手がかり / 判定材料なし)
  - **「判定材料なし」がSNS経由の画像では最も多い**。これは失敗ではなく通常の結果です
- 根拠は **1件ずつ、4段階の重み(AI痕跡 / 実写材料 / 注意 / 情報)つき**で示される
- 抽出した生のメタデータは**全部見られる**(必要な人だけが)
- **別枠の実験機能**が1つあります(§6)

### 4-2. AICHECK で通らなければならない道筋

```
18件のリスク項目を見て当てはまるものにチェック → 4件の信頼シグナルでスコアを下げる
→ スコアと3段階の帯を見る → 帯ごとの助言に従う → (必要なら)結果を持ち出す
```

- 全22項目(リスク18 + 信頼4)には**重みが公開されている**(採点が透明であること自体が機能)
- 各リスク項目には**「なぜそれがシグナルなのか」の説明**が付く
- チェックのたびに**即座に**結果が変わる
- 一部の項目は**決定的**で、それ1つで下限スコアが保証される(他が0でも埋もれない)
- 22項目は**多い**。スマートフォンでは相当な縦の長さになります。ここが最大の離脱点です

### 4-3. BADGE で通らなければならない道筋

```
相互リンク証明の仕組みを理解する → 6項目を入力する → 生成物を確認する
→ ダウンロードする → 自分の管理下で公開する → 全SNSのプロフィールにURLを書く
```

- **最後の1手(全SNSのプロフィールに証明ページURLを書く)を忘れると、証明は成立しません。**
  この重みが伝わる必要があります
- 入力してみるまで**何が手に入るのか分からない**のが現在の弱点です

## 5. 果たされるべき能力(Function Presence)

**どう表示するかは指定しません。** 存在の必要性だけを述べます。
機械可読版は `FUNCTION_PRESENCE_CONTRACT.json` です。

- `CAP-CHECKER`(画像来歴チェッカー)— **primary**。HOMEで存在が認識でき、到達できること
- `CAP-ACCOUNT`(AIアカウント鑑定)— **primary**。同上
- `CAP-BADGE`(実在証明バッジ)— **primary**。同上
- `CAP-EVIDENCE`(実測レポート)— **secondary**。信頼の根拠なので、HOMEから到達できること
- `CAP-DIRECTORY`(実在クリエイター名鑑)— **secondary**。到達できること
- `CAP-BUSINESS`(法人向け)— **secondary**。唯一の収益導線。到達できること
- `CAP-DOCS`(説明書)— **secondary**。到達できること
- 法務3文書 — **tertiary**。全画面から到達できること(視覚的に目立つ必要はないが、DOMに必ず存在)

### 5-1. 情報構造についての未解決事項(そちらの決定事項)

**11画面をどう束ねるかは決まっていません。決めてください。**

事実として:

- 最も狭い検証幅は **360px** です。ここで11画面すべてへの導線が成立する必要があります
- `REPORT` はこのプロジェクトの信頼の根拠ですが、一般利用者(①)にとっては本題ではありません
- `BUSINESS` は唯一の収益導線ですが、利用者の大半(①)には無関係です
- 一般利用者(①)と法人(③)では、必要な画面がまったく違います

## 6. 特殊な事情(設計判断に効くもの)

### 6-1. 90MB のダウンロードを伴う実験機能

`CHECKER` には、メタデータが消えている画像のための **実験的な追加判定**があります。

- 画像そのものを学習済みモデルで判定します
- **モデルは約90MB。初回だけダウンロードが必要**(2回目以降は端末内キャッシュ)
- 判定に約0.8秒。**単一スレッドで動くため、実行中は画面が重くなりえます**
- **PC推奨**(スマートフォンでは重い)
- 押すかどうかは**利用者が明示的に決める**。既定では走りません
- ただし「次回から自動で実行」を選ぶこともできます
- **これは実験機能であり、メタデータによる本判定とは別枠**です。同格に見えてはいけません
- 結果は3段階。どの段階にも固有の限界の説明が付きます

**設計上の難所:** 「90MBかかる」「実験である」「参考値である」「どこまで当たるか」を、
押す前に理解させる必要があります。

### 6-2. 待ち時間が2種類ある

1. **メタデータ解析**(数秒)— メインスレッドで走る。最大300MBのファイルを受け付ける
2. **モデルのダウンロード + 推論**(初回は数十秒〜)— 進捗をバイト数で示せる

どちらも、**メインスレッドが詰まっても止まって見えない待ち表現**が必要です。

### 6-3. 名鑑には実在の掲載が0件

`CREATORS` には現在、**実在の掲載者が1人もいません。**
並んでいるのは「どんな項目が載るか」を示すための**見本**で、
**架空の人名は意図的に付けていません**(実在を売る名鑑で架空の人物をでっち上げるのは筋が通らないため)。

この事実は**見本より先に読める必要があります**。空っぽに見えることと、
募集中であることを、同時に成立させる必要があります。

### 6-4. 数表が多い

`REPORT` と `BUSINESS` には比較表が複数あります。
**360px幅で、表の内容が最後まで読める**必要があります(ページ全体が横スクロールしてはいけません)。

## 7. 破ってはいけない配置制約

**これは Layout Suggestion ではなく、製品の安全要件です。**

| ID | 制約 |
|---|---|
| `PL-1` | `AICHECK`: 結果を持ち出す操作(コピー・画像保存)より **前** に、晒す使い方への警告が読めること。折りたたみの中に入れない。持ち出し操作より目立たなくしない |
| `PL-2` | `CREATORS`: 「実在の掲載は0件で、並んでいるのは見本」の注意が、見本より **前** にあること |
| `PL-3` | `CHECKER`: 判定の限界の説明が、結果を読んだ **直後** に読めること |
| `PL-4` | `CHECKER`: 実験的な画素判定が、メタデータによる本判定と **同格に見えない**こと |
| `PL-5` | `BADGE`: 「全SNSのプロフィールにURLを書く」手順が、ダウンロード導線と同じ画面で見落とされない位置にあること |
| `PL-6` | `CHECKER`: 90MBのダウンロードと実験機能である旨が、実行操作より **前** に読めること |
| `PL-7` | 全画面: 法務3文書へのリンクが DOM に存在すること(視覚的に目立つ必要はない) |

これ以外の配置・順序・グルーピング・視覚的階層は、**すべてそちらの決定事項です。**

## 8. 必ず入る文言

`REQUIRED_COPY.json` を参照してください。2種類あります。

- **verbatim** — 自動検査が完全一致で見ています。1文字も変えられません
- **meaning** — 書き換えてよいが、意味・強さ・限定条件を弱めてはいけません

`REQUIRED_COPY.json` に現行の文言が入っていますが、**これは「今こう書いてある」という事実の記録であり、
文言案の要求でも、視覚的な扱いの指定でもありません。**
`meaning` の項目は、より良い文言に置き換えていただいて構いません。

`REQUIRED_COPY.json` に現れる記号類は文言の一部ではありません。
アイコン言語(何を、どう記号化するか)は**そちらの決定事項**です。

## 9. 技術的な制約(実装可能性の境界)

`TECHNICAL_CONSTRAINTS.json` に全文があります。設計判断に直接効くものだけ再掲します。

### 9-1. 使えないもの

- **外部からの読み込みが一切できません。** Content-Security-Policy で
  外部オリジンの script / style / **font** / image / fetch が全てブロックされます
  - → **Webフォントは使えません**(Google Fonts 等)。使えるのは **OS標準フォント**と、
    リポジトリに同梱した自作アセットだけです
  - → 外部アイコンフォント・外部アイコンライブラリも使えません
- **新しい実行時ライブラリを増やせません。** アニメーションライブラリ・UIライブラリは追加不可。
  モーションは **CSS と Web Animations API** の範囲で実装します
- サーバー処理・DB・ログイン・セッションはありません(静的サイト)
- Service Worker がないため、**オフラインでは動きません**。この点を主張してはいけません

### 9-2. 画像素材について

- **人物・顔・手を描いた画像は一切使えません。**
  AI生成画像で人物を描くとこのプロジェクトの主張と矛盾するため。実写の人物写真も権利上使いません
- 他者の画像を持ち込めません
- 使えるのは **抽象図形・幾何学模様・器具/レンズ等のモチーフ・自作の図解・自作のSVG**
- **現在、自作の画像アセットは共有用のOG画像1枚しかありません。**
  ロゴ画像・アイコン画像・イラストは**存在しません**。必要なら**新規に定義してください**
  (実装は SVG / インライン描画で行います)

### 9-3. モーションの制約

- `prefers-reduced-motion` への対応は必須
- 優先: `transform` / `opacity` / コンポジタで完結するプロパティ
- 避ける: 不要な無限アニメーション、レイアウトスラッシング、大面積の animated blur、
  スクロール乗っ取り、長時間ブロックするアニメーション、同時多発的なモーション
- **推論中(単一スレッド)と解析中(メインスレッド)は、重いモーションを走らせられません**

### 9-4. 検証条件

- 幅 **360 / 390 / 430**(DPR3)
- **light と dark の両方**。ダークは自動追従のみで、手動切替UIは現状ありません
- 日本語の長文・長い固有名詞・数表が崩れないこと

## 10. 書いてはいけないこと(捏造の禁止)

以下はいずれも**存在しません**。デザイン上の説得力のために書き足さないでください。

- 利用者数・導入実績・受賞歴・顧客ロゴ・推薦の声
- 認証・認定・公的機関・第三者監査(**第三者による再測定は行われていません**)
- 有料プラン・課金・トライアル(全ツール無料)
- `TRUST_AND_SAFETY_FACTS.json` の `measured_numbers` に無い精度の数値
- 「AI生成でないことを証明できる」という主旨の表現
- 判定に対する「100%」「確実に」「必ず」

## 11. 返していただきたいもの

`DESIGN_RETURN_SCHEMA.json` と `CHATGPT_INSTRUCTIONS.md` に厳密な形式があります。概略:

**文書**
- `DESIGN_DECISION.md` — Visual Direction とその理由
- `DESIGN_SYSTEM.md` — Color / Typography / Spacing / Surface / Icon / State の言語
- `SCREEN_SPEC.md` — 画面ごとの構成・階層・状態の見せ方
- `MOTION_SPEC.md` — モーションの目的・対象・カーブ・時間・reduced-motion時の挙動
- `ASSET_MANIFEST.json` — 必要なアセットの一覧
- `DESIGN_RETURN_BINDING.json` — 対応関係の宣言

**ビジュアル**
- `HOME_MASTER` — BRAND_CRITICAL 画面
- `TASK_MASTER` — TASK_CRITICAL 画面
- `STATE_VISUALS` — 状態の見せ方

**画面の役割分担についてのお願い**

`HOME` は BRAND_CRITICAL(Visual impact / worldbuilding を優先)、
`CHECKER` / `AICHECK` / `BADGE` / `CREATORS` は TASK_CRITICAL
(clarity / hierarchy / trust / task completion を優先)として扱ってください。

**HOME の装飾密度を Task 画面へ機械的にコピーしないでください。**
ただし、Color Language / Typography Family / Signature Motif / Icon Language /
Surface Language / Motion Character は**同一の Design Language を維持**してください。

## 12. 実装側の約束

- Design Return を Design Source of Truth として凍結し、忠実に実装します
- 「自分ならこうする」という変更は加えません
- 機能・状態・文言の意味は1つも壊しません
- 未定義の Design Decision を見つけた場合、自分で補完せずそちらへ返します
