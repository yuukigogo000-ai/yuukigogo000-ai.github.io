## 1. 文体特徴 → 指示書に入れた既定値

- **長さ**: 20代前半15〜30字/1〜2文、20代後半〜30代30〜60字/2〜3文。相手の直近3通の平均長±30%に追従。「短すぎ」は「長すぎ」より嫌われる。相手が「笑」だけに5行返すのはAI/おじさん判定 [データ+事例]
- **句読点**: 「、」は使う(U30でも友人宛47.9%が使用)、文末「。」は落とす。LINEでは「!」が句点の代わり(筑波大2024の研究)。30代は「。」1個まで許容 [データ]
- **笑い**: 「笑」1個が最も安全。「w」は親密化後。「(笑)」「www」「草」は古い/馬鹿にしてる印象。面白くない所の「笑」は地雷 [データ+事例]
- **絵文字**: 0〜1個/通。🙏😂🍜など具体物。😊😅💦✨❗の常設・赤❗・🥺・♪多用が「おじさん感」の主因(Pairs Q&A複数・Simeji1位) [データ+事例]
- **敬語**: 会うまで「です・ます」骨格+「〜ですね!」「〜です笑」。初手タメ口NG2位、カタカナ語尾NG、「だお/ワロタ」は7割が幻滅 [データ]
- **質問**: 1通1問、2〜3通に1回は質問なし。「お仕事は?休日は?」連打はアンケート、オウム返し+質問は「ノウハウの誤実践」と見抜かれる [データ+事例]
- **生活感**: AIが一番バレるのは「今日何してたかが1ミリも滲まない」「誤字ゼロ改行完璧」「相手のテンションに関係なく同じ調子」(女性ライター証言) [事例]
- **挨拶だけ送らない**: 「おはよう」「今日も一日〜」の日報型は重い [事例]

## 2. AI/テンプレ/おじさん判定される表現(禁止リストとして実装)
「プロフィール拝見しました!」「素敵ですね」「ぜひ」「いかがでしょうか」「〜かと思います」「〜させていただきます」「承知いたしました」の連続 / 「〜ですね。〜ですね。」の同リズム・毎通同じ長さ・毎通質問締め / 「よろしくお願いいたします。」で必ず締める・時候の挨拶 / 😊😅💦✨❗常設・「(笑)」・「www」・「〜だネ」「〜カナ」・「○○ちゃん」 / 「やっと可愛い子に〜」「今夜空いてる?」「今度会えたら嬉しいな」の初手距離詰め / 温度ゼロの文(「本当ですね。今日は気温が高かったので体調管理が大切ですね。水分補給はされましたか?」)

## 3. 成功パターン(指示書の「誘い」「LINE交換」「日程」「前後」「追い」に実装)
- **初回**: いいねした理由+共通点+質問1つ、下の名前を名乗る(Pairs女性2,291名調査)。「はじめまして○○です。よろしくお願いいたします。」だけは返しようがない
- **誘い**: 10〜15往復・1〜2週目安。会話に出た店に紐づけ、直球「一緒に行きません?」+曜日/時間帯2択。「次は〇〇行きたいですね〜」の反応待ち・「どうしましょう?」の相談型は頼りない(女性証言) [データ+事例]
- **LINE交換**: ①デート約束直後(「当日の連絡用に」) ②10往復以上後 ③初デート後。3往復以内は業者/ヤリモク疑い。理由は「通知見逃しがち」。断られたら即引く [データ+事例]
- **日程調整**: 候補2つ提示・店はこちらが決める・「いつでも空いてます」NG・「土日休みですよね」の前置き不要 [事例]
- **前日**: 21時前に待ち合わせ確認+楽しみ1〜2文。「ちゃんと来てくれる?」は催促 [データ]
- **お礼**: 当日中に「ありがとう+楽しかった+具体的話題+次の店」。「また機会があれば」「ありがとうございました」一文のみ・長文感想・告白調NG [データ]
- **追い**: 3日〜1週間あけて1回、報告型・返信不要型。「返信ないですけど?」「覚えてますか?」「おはようございます!」は即ブロック級 [事例]

## 4. 証拠の限界
- 「1返信を何吹き出しに分けるか」「年代別の『!』『〜』使用率」の直接調査は見つからず(観察記事・証言のみ)
- 「AIっぽさ」の女性側認識は日本では定量調査ゼロ(女性ライター証言と米Arrows社調査のみ: 「AI疑いでゴースティング約20%」「Z世代75%がAIは人工的」)

- LIFRELLのランキングはSNS投稿の分類、ラス恋研究所の数値は出典未記載

## 4.5 改訂記録: 固有名詞の捏造対策(2026-09-01)

pricing_eval の本番プロンプト追従テスト(3モデル×30合成ケース・正本 `pricing_eval/runs/fidelity_20260901_*/results.jsonl`)で、次の2つを**実測**した [データ]:

1. **架空の体験談つき施設名の発明**: 入力に無い施設名を「最近アクアマリンを行ってきたんですけど、アザラシの写真ばっかり撮ってました笑」のように本人の体験として生成(Ministral 14B)。送信者は次のターンで答えられなくなる
2. **REPLY_SYSTEM 例文の固有名詞の流用**: 良い例に含まれる「高尾山」「代官山」等を、入力に無いのに返信へ混入(Ministral 4件 / Qwen3 VL 3件 / Kimi K2.5 1件)

対策として REPLY_SYSTEM「# 誠実さ(絶対)」へ1行追加(例文名の流用禁止・入力に無い場所を既知の体で書かない・提案は「行ってみたい」形に)。あわせて UI 側に検出器 `src/lib/ungrounded.mjs`(入力に無い固有名詞の警告バッジ)を追加した。スクショ内の文字は照合できないため、これは警告であってブロッカーではない。

## 4.6 改訂記録: 脈あり度(interest_level)の除去(2026-09-01)

料金決定レビューで「脈あり度が復活している。以前の決定と矛盾し、人物・感情評価リスクも上げる」と指摘され、発注者GOで製品から除去した [決定]。

- REPLY_SCHEMA から `interest_level` を削除(required からも)。UIの「脈あり度」メーター(`ReplyTab.tsx`)を削除。「いまの状況」(situation)と「次の一手」(advice)は残す
- REPLY_SYSTEM 内で interest_level に言及していた3箇所(スクショの読み取り/短文化時/誠実さ)を situation・advice への事実ベース反映に書き換え、「# 誠実さ(絶対)」に**数値・パーセント・「脈あり/脈なし」断定での評価禁止**を1行追加
- 引き際の助言(深追いしない選択肢を示す)は残す。数値化をやめただけで、コーチングの中身は落としていない
- Codex破壊的検証(r1/r2)の指摘で、「温度感」は**会話の状態**(続きやすい/続きにくい)として観測事実を根拠に書く形へ統一し、スタンプのみ返信の「会話を広げる気が薄い」(相手の意図の推定)も会話状態の表現に書き換えた。situation の役割=会話の状態説明、advice の役割=次の一手と引き際、のどちらも相手の気持ちの断定はしない
- 評価器(`pricing_eval/src/lib/fidelity_checks.mjs`)は interest_level が出力に含まれていたら schema_failure(禁止出力)として落とす。追加30ケースは除去後のこのプロンプトで測る

## 4.7 改訂記録: 3案の件数固定とプレースホルダ禁止(2026-09-01)

追加30ケース確証run(b2)の実測 [データ]: Kimi K2.5 が tool-use でも `replies` を6件返した(TXT_SHORT_07)。REPLY_SCHEMA が件数を縛っていなかった。別ケース(TXT_SHORT_06)では店名・相手の名前を「○○」で出力し、そのまま送れない文になった。

発注者決定 [決定]: (b) REPLY_SCHEMA.replies に `minItems: 3, maxItems: 3` + (c) tool 説明文とプロンプトに「必ずちょうど3件。4件以上・2件以下は禁止」。あわせて「○○」「〇〇」「［店名］」「〈場所〉」等の穴埋め記号を禁止し、固有名詞が不明なら「気になるお店」「最近読んだ本」のような自然な一般表現に置き換える規則を「# 誠実さ(絶対)」へ追加。相手の名前が分からなければ名前を呼ばない。

限界: `minItems/maxItems` はモデルへの制約で絶対保証ではない(6件事例が tool-use で起きた)。本番ではサーバー側で独立に schema 検証し、内容検査を通った先頭3件のみ返す。3件未満・禁止出力・未解決プレースホルダは1回だけ再生成、再失敗はエラー(回数は消費しない)。評価では4件以上を引き続き違反として記録する。

## 4.8 改訂記録: Kimi K2.5 不採用・NG/OK例の追加・検出器の位置づけ(2026-09-01)

実測 [データ]: 規則を強化し temperature 0.2 にした確証run(TXT_SHORT_07×5・tool-use)は自動評価では 5/5 通過だったが、人間確認で 5/5 に入力に無い固有名詞・ブランド・体験談(「中目黒のとりきち」「鳥貴族」「先週行ったところがあって」等)が出た。検出器(カタカナ語の体験文脈・施設接尾辞・例文名・プレースホルダ)は漢字・ひらがなの店名と体験談を素通しした。

発注者決定 [決定]: **Kimi K2.5 は不採用**(追加のプロンプト調整・07再実行・30件runは行わない)。次候補 Qwen3 VL 235B を同条件で10件(飲食2/旅行2/本・映画2/趣味・ブランド2/個人体験2・未見ケース)から再評価。REPLY_SYSTEM「# 誠実さ(絶対)」に NG→OK 例を5分類で追加(焼き鳥・特定の地名・店名だけに過適合しないよう、例には固有名詞を入れず「〇〇(地名)」のような説明記号で書く)。

検出器の位置づけ [決定]: 拡張は**補助的な候補提示に限定**する。停止層は実在名の固定リスト(有名チェーン・ブランド)と従来の規則、補助層(`fabrication_hint`)は「地名+店名」「先週…行った」等の言い回し。**未知の漢字・ひらがな固有名詞を完全に検出できるとは記載しない**。最終判断は人間確認ページで全件を見る。

Qwen3 VL 235B の限定評価 [データ]: **Qwen3 VL 235B 10件 run の結果(2026-09-01 夜・run `fidelity_tooluse_qwen_fab10`)= 不合格・5件目で停止**: 初回違反 2件(FAB_TRAVEL_01「草津温泉」=入力に無い地名 / FAB_MEDIA_01「〇〇」「△△」「□□」プレースホルダ)、再生成後も FAB_MEDIA_01 が「〇〇」を再発(最終違反1件)→停止(初回違反上限1も超過)。自動通過した4件も人間確認では **3件に捏造**(FAB_TRAVEL_01 再生成後「箱根とか気になってる」/ FAB_TRAVEL_02「自分はバリとハワイだけ」「バリはウブド、ハワイはオアフ」= 架空の渡航歴 / FAB_FOOD_01「自分も週1で食べてます」「焼き餃子派」= 架空の習慣)と、3件で相手の名前を「相手さん」と書く未解決の代名詞。人間確認で問題なしと言えるのは FAB_FOOD_02 の1件のみ。費用 $0.0190(7呼び出し・≈3.0円)・latency 4.7〜5.9秒。補助候補層に地名リスト(箱根・バリ・ハワイ等)と自己申告パターン(「自分は〜派」「週1で」)を追加し、「相手さん」をプレースホルダ規則に追加した(いずれも候補提示/そのまま送れない文の検知であって、捏造の完全検出ではない)。**Opus 5(アプリ本来のモデル)で同じ10件評価を試行(2026-08-31 夜・run `fidelity_tooluse_opus5_fab10`)→ 権限で実行不可**: Bedrock 東京アカウントには `anthropic.claude-opus-5`(global inference profile。国内固定の jp. プロファイルは未発見=処理が国外へ出得る)が存在するが、評価用 IAM ユーザー replier-eval-cli の identity policy が `bedrock:InvokeModel` を許可していない(AccessDeniedException・requestId 93cd9203…・1呼び出し・トークン非課金)。規則により私はポリシー拡大・モデルアクセス操作をしない。Anthropic API 直接のキーも環境に無い。価格は AWS 公式ページが機械取得できず、Anthropic 公式 $5/$25 per MTok に安全係数1.1を掛けた推定(`--allow-estimated-price` 明示時のみ)で予算計上する仕組みを追加済み。

**結論: 2モデルとも「入力に無い事実を足さない」を規則だけでは守れない。**次の手(別モデル / サーバー側での一般表現置換 / 自分の事実を入力欄で渡す UI)は発注者判断。結果画面には「AIによる返信案です。内容が事実と合っているか確認してから使用してください。」を常設(非妨害的)。
