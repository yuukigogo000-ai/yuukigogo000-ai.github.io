# BLIND DESIGN BRIEF — パチスロ帝国

このブリーフは **WHAT(何を満たす必要があるか)** だけを記述する。
**HOW(どう見せるか)** は一切含まない。視覚表現・構成・色・書体・装飾・動きの人格は、
すべて Design Authority が決定する。

既存実装の視覚表現に関する情報(スクリーンショット、CSS、色、書体、余白、構成、
既存の視覚的比喩、既存の装飾)はこのパッケージに **意図的に含めていない**。
既存の見え方に引きずられずに設計してよい。

---

## 1. この製品は何か

架空のパチンコ・スロット店を経営し、**1営業日ずつ意思決定を重ねて純資産1億円を目指す**
シミュレーションゲーム。単一のWebドキュメントで動作し、サーバーもアカウントも存在しない。

この製品には性質の異なる2つの柱がある。

1. **経営(判断)**: 出玉設定と経営施策を決め、1日を実行し、結果を読み、次の判断へ活かす。
2. **遊技(体感)**: 自店に置いた架空の実機を利用者自身が操作して遊ぶ。当選の瞬間そのものが価値。

この2つは同じ製品の中に共存する。片方だけが成立しても製品としては不十分である。

## 2. 中心にあるジレンマ(製品の核)

出玉設定を **渋る** と当日の利益は増えるが、評判が下がり固定客が離れ、行政指導のリスクが高まる。
出玉設定を **出す** と客と固定客が増えるが利益は減り、勝ち目当ての専業客(プロ)に狙われる。

利用者が毎日向き合うのはこの緊張であり、製品の設計上もっとも重要な事実である。
「全台一律」ではなく「出す台と回収する台を作り分ける」判断が上達の本体になる。

## 3. 誰のためか

- パチンコ・スロット文化に馴染みがある日本語話者のカジュアルゲーマー
- 経営シミュレーション/タイクーン系のやり込みを好む層
- 実機の遊技経験がなくても遊べる想定(専門用語には製品内で説明が与えられている)

## 4. 利用者の主要な意図

| 意図 | 頻度 |
|---|---|
| 今日の設定と施策を決めて1日を実行する | 毎日(セッションの中心) |
| 実行結果を読み、何が効いたかを理解する | 毎日 |
| 資金を再投資して店を成長させる | 数日ごと |
| 実機を遊技して出方を体感する | 任意のタイミング |
| 過去の営業成績を検証する | 数日ごと |
| 目標(純資産1億円)への距離を確認する | 常時 |

**1セッションのリズム**: 状態を見る → 判断する → 1日を実行する → 結果を読む → また判断する。
このループが何十回も繰り返される。ループの摩擦は製品体験を直接損なう。

## 5. 必ず存在しなければならない能力

`FUNCTION_PRESENCE_CONTRACT.json` に、能力ごとの重要度と存在要件(最初の文脈で存在を
認識できる必要があるか / 作業中に必ず利用可能である必要があるか / 到達可能である必要があるか)を定義した。
**表示方法は指定していない。**

機能の完全な定義は `FUNCTION_FREEZE.json`(F-001〜F-045)にある。
これらは1つも欠けてはならず、意味を変えてもならない。

## 6. 必ず表現し分けなければならない状態

`SCREEN_STATE_INVENTORY.json` の `states`(S-ID)を参照。要点のみ挙げる。

- 通常操作可能 / 選択済み / 実行不可(条件未達) / 実行確認待ち
- 実行中 → 結果提示 → 復帰の遷移
- 警告(スタッフ不足・警戒度上昇・人気の枯れ・赤字)と危険(指導リスク)
- 空(設置台なし・営業履歴なし)
- 達成(目標到達)と終局(倒産。やり直す以外を受け付けない)
- 遊技中の状態: 待機 / 回転中 / リーチ / 当選 / 連チャン継続 / 自動進行中 / 残数切れ

**当選と非当選、黒字と赤字、警戒水準の高低は、色だけに依存せずに判別できなければならない。**

## 7. 扱う情報の実際の量(設計上の事実)

- 常時把握が必要な経営指標: **7項目**
- 機能領域: **4つ**(切り替え方法は未指定)
- 設置される台: **最大60件**。台ごとに 名称 / 短い説明 / スペック概要 / 人気水準 /
  前日の収支と客数 / 売却額 / 状態標識(最大3種) / 設定の選択 / 遊技の起動 / 売却 を伴う
- 購入対象の機種カタログ: **10件**
- 営業成績: 1日あたり **8項目** × 最大60日
- 損益の推移: 直近 **30日**
- 1営業日の結果に含まれる項目: 発生イベント文(0〜複数件) + 収支4項目 + 客数の内訳 +
  台別収支(最大60件) + 7日ごとの週次レポート
- 1営業日あたりのイベント文: 最大29文字の短文
- 実績: **15件**
- 遊技中に参照される数値: スロット5指標 / パチンコ5指標

この密度を破綻なく収容できることが要件である。密度をどう扱うか(要約・段階開示・
優先付けなど)は Design Authority の判断に委ねる。

## 8. 遊技(実機)体験の要件

- 遊技は **利用者の操作で進行する**。スロットは開始操作と3回の停止操作、
  パチンコは回転操作(または自動回転の切り替え)。
- **当選の瞬間が体験の主役**である。当選・リーチ・連チャンの継続は、
  利用者が見逃さずに認識できなければならない。
- 遊技は経営の収支に影響しない体験モードであり、その事実が利用者に伝わる必要がある。
- 残数(メダル・玉)が尽きても無償で補充して続けられる。
- 遊技はいつでも終了して経営へ戻れる。

## 9. コピー

`REQUIRED_COPY.json` を参照。`literal: true` は文字列として保持、`literal: false` は
意味を保持すれば文言調整可。**存在しない機能・保証・実績を示すコピーを作ってはならない。**

既存実装ではラベル先頭に絵文字が付いているものがあるが、**アイコン言語(絵文字の採否と種類を含む)は
Design Authority の決定事項**であるため、ブリーフでは絵文字を除いた本文のみを提示している。

## 10. 信頼と安全の事実

`TRUST_AND_SAFETY_FACTS.json` を参照。特に:

- 機種・メーカー・演出はすべて架空。実在の製品を指してはならない。
- 現金・課金・実際の賭博は存在しない。現実の賭博で勝てると受け取れる表現は不可。
- 個人情報の収集・外部送信・トラッキングは一切ない。
- セーブは利用者のブラウザ内にのみ存在する。
- オンライン機能・アカウント・クラウド保存・ランキングは **存在しない**。存在を示唆してはならない。

## 11. 技術制約(設計の実現可能性に直結する)

`TECHNICAL_CONSTRAINTS.json` に全文。設計判断に効く要点:

- **単一の自己完結HTMLファイル**。ビルド工程なし、外部リクエスト禁止。
- **Webフォントは使用不可**。OS標準フォントスタックのみ。日本語表示必須。
- 追加アセットはインライン(SVG / CSS / data URI)または同梱静的ファイルに限る。総量は軽量に保つ。
- **必須対応幅: 360 / 390 / 430 px**。加えてデスクトップウィンドウ(1080px)でも破綻しないこと。
  ページ全体の横スクロールは禁止(幅の広いデータはその要素内で横スクロールさせる)。
- **prefers-reduced-motion: reduce への対応が必須**。
- アニメーションは合成向きプロパティ(transform / opacity)優先。常時再生の無限アニメーションは最小限。
  広範囲の大きなぼかしアニメーション、スクロール乗っ取り、進行を止める長い演出は不可。
- 動的に挿入される文字列をHTMLとして解釈させない実装が必要(注入対策)。
- PWA/デスクトップ配布のため、既存のアイコンファイルパスと寸法(192px / 512px)と
  単一のテーマ色値が技術的に必要。**絵柄と色そのものは Design Decision。**

## 12. 動き(モーション)に求められる役割

モーションは次の3目的のいずれかに該当する必要がある。

1. **フィードバック**(操作が受理されたことを伝える)
2. **状態遷移**(実行 → 結果、当選の発生、警告の出現など)
3. **ブランドモーション**(製品の性格を伝える)

装飾のためだけの動き、進行を待たせる動き、同時多発の過剰な動きは不可。
`reduce` 指定時は、意味の伝達を損なわずに動きを止められる設計であること。

## 13. 画面の役割分類(Design Authority が守るべき区分)

- **BRAND_CRITICAL**: 導入(オンボーディング)、遊技(スロット/パチンコ)
  → 世界観と体験の強度を優先してよい文脈。
- **TASK_CRITICAL**: 経営の各作業文脈、1日の実行、結果の理解、記録の検証
  → 明快さ・判断のしやすさ・信頼性・作業完了を優先する文脈。

BRAND_CRITICAL の装飾密度を TASK_CRITICAL へ機械的に持ち込まないこと。
ただし両者は同一のデザイン言語(色の語彙 / 書体ファミリー / シグネチャモチーフ /
アイコン言語 / 面の扱い / モーションの性格)を共有すること。

## 14. Design Authority が決定すべき事項(未定義)

以下は **意図的に未定義** である。Claude Code 側では決定しない。

1. ビジュアルディレクション全体と製品の雰囲気
2. 色の人格と配色体系(明暗の扱いを含む)
3. 書体の人格と文字の階層
4. 4つの機能領域を行き来する仕組みの提示方法
5. 常時参照される7つの経営指標の提示方法
6. 主要アクション(1営業日の実行)の提示方法
7. 最大60件になる台の一覧の扱い方(密度・要約・段階開示など)
8. 1営業日の結果の提示方法(復帰までの流れを含む)
9. 遊技体験の視覚表現(実機の見立て、当選演出の強度)
10. 損益推移の表現方式と、黒字/赤字を色以外でも判別させる方法
11. 状態(警告・危険・実行不可・空・終局)の視覚的表し方
12. シグネチャとなる視覚要素とモーションの人格
13. アイコン言語(絵文字を用いるか否かを含む)
14. アプリアイコン(192px / 512px)とテーマ色値の絵柄・色

## 15. 禁止事項

- 既存機能(F-001〜F-045)の削除・追加・意味変更
- 状態(S-ID)の削除
- コピーの意味の変更、および存在しない機能・保証の示唆
- 1営業日の実行を自動化・省略すること
- 遊技が経営収支に影響するようにすること
- 破壊的操作(売却・やり直し)から実行確認を取り除くこと
- 外部ネットワーク依存(Webフォント・CDN・外部画像・解析)の要求
- ビルド工程を前提とする設計
- 対応幅(360 / 390 / 430)で成立しない設計
