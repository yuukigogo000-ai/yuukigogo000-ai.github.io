## 5. 評価基準(3層)

**HARD — 機械・1件でも不合格**(uicheck が数える)
- console error / pageerror 0
- 横はみ出し(overflow-x)なし(360px でも)
- 入力欄(input/select/textarea)の文字 **16px以上**(iOS の自動ズーム防止)
- 外部フォント読込なし(`fonts.googleapis` 等)
- `100vh` を使わない(iOS の下部バー問題 → `100dvh` か `min-height` 別解)

**METRIC — 機械・基準線より悪化禁止、WOごとに目標値**(uicheck が数える)
- タップ領域 <44px の要素数(目標: 主操作・タブ・ボタンは 0)
- コントラスト不足(通常文字 4.5 / 大文字 3.0 未満)の要素数
- 実測の文字サイズ種類数(目標 ≤5〜6)・角丸種類数(≤3)・文字色種類数・背景色種類数
- CSS 内の `:root` 外 生16進の数(目標 0)・`font-size` 宣言の種類数・`border-radius` 宣言の種類数

**HUMAN — あなたが見本と横並びで判定(Claude は判定しない)**
- 画面の主目的が1つに見えるか/最重要操作が一番目立つか
- 見本と比べて劣る点(余白の詰まり・文字の階層・色の使い方)
- 片手・親指で主操作に届くか(下部 1/3 に主操作)
- 状態ごと(空/読込中/エラー/オフライン)に「次に何をすればいいか」が分かるか

**スマホWeb特有の約束事**(実装時のチェックリスト。HARD/METRIC で拾えないものは差分レビューで見る)
- Safe Area(`env(safe-area-inset-*)`)・`viewport-fit=cover`
- hover 前提の操作を作らない(タッチにhoverは無い)
- 主操作は下部・固定ヘッダーは薄く・キーボード出現時に主ボタンが隠れない
- `inputmode` で数字キーボード・`autocomplete` 適切に
- ダークモード両対応(`prefers-color-scheme`)・システム文字拡大で崩れない(rem/em)
- フォントは system-ui 系スタック(オフライン前提)

## 6. スクショと検査の固定条件

`uicheck.mjs` にハードコード。**変えたら基準線を取り直す。**
- ビューポート: `android-s` 360×800 / `iphone` 390×844、DPR 3、タッチ有効
- カラースキーム: light / dark 両方
- ロケール ja-JP
- 出力: `ui-workbench/uicheck/out/<app>/<時刻>/` に `*_light.png` `*_dark.png` `*_full.png` `report.md` `report.json`、`latest.json` を更新(`out/` は git 無視)。**正式な基準線は `ui-workbench/uicheck/baselines/<app>.json` にコピーして git 管理**(WO 完了時に after を新基準線として更新)
- 横並び画像は **同じビューポート・同じスキーム**で見本と実装を並べる(見本が別サイズなら幅を合わせて縮尺、加工はしない)

## 7. 状態の再現

空/読込中/エラー/オフライン/成功 の各状態は**スクショに写らなければ検査していない**。
- アプリ側に URL クエリで状態を強制できるフック(例 `?state=empty`・`?state=error`)が無ければ、**WO 内で先に足す**(本番では無視される安全な実装にする)
- 検査器は `--state state=empty` で同じ条件で撮る
- 状態ごとの HUMAN 判定は「次に何をすればいいか分かるか」

## 9. 道具

**uicheck(機械検査器)** — `ui-workbench/uicheck/uicheck.mjs`(Playwright/Chromium。`ui-workbench/uicheck` で `npm install` 済み)
```
# 基準線(初回)。Git Bash では MSYS_NO_PATHCONV=1 を付ける(/band/ がWindowsパスに化けるため)
MSYS_NO_PATHCONV=1 node ui-workbench/uicheck/uicheck.mjs --path /band/ --name band
# 変更後: 基準線と比較。悪化があれば RED(exit 1)
MSYS_NO_PATHCONV=1 node ui-workbench/uicheck/uicheck.mjs --path /band/ --name band --baseline ui-workbench/uicheck/baselines/band.json
# 自己検査: 既知の欠陥4種を注入して検出できるか(検出できなければ exit 2)。検査器を直したら必ず回す
MSYS_NO_PATHCONV=1 node ui-workbench/uicheck/uicheck.mjs --path /band/ --name band --mutate
# 状態の再現
MSYS_NO_PATHCONV=1 node ui-workbench/uicheck/uicheck.mjs --path /band/ --name band-empty --state state=empty
```
判定の読み方: 1行目 `GREEN` / `RED [hard: …]`(元からのHARD違反・悪化なし)/ `RED [regression: …]`(基準線より悪化)/ 両方。exit 0=GREEN、1=RED、2=自己検査で仕込みを見逃し。2026-08-17 に GREEN(HONMONO)・RED hard(セトリズム)・RED regression(細工基準線)・変異4/4 の全経路を実証済み。
限界(正直に): Chromium のみ(iOS Safari 実機の代わりにならない → G7)/グラデーション・画像背景の上の文字はコントラスト判定不能(`contrast_unknown` に数を出す)/SW 登録は http(localhost) では false になりうる/近似器であって審美眼ではない。**HUMAN 判定の代わりにしない。**
検査器を触ったら `--mutate` で 4/4 検出を再確認してから使う(2026-08-17: 4/4 RED OK 実証済)。
